# 3-1. 테스트 코드와 테스트 주도 개발

# 이번 주제

* 테스트와 테스트 주도 개발에 대해 이해합니다.
* 테스트 코드를 작성하고 적용해보는 시간을 가집니다.

# 발표 내용

## 테스트와 테스트 주도 개발

**👽 테스트 ?**
- 내가 만든 코드가 기대한 대로 동작하는지 확인하는 과정
- 사람이 직접 실행해보며 확인할 수도 있고, 컴퓨터가 자동으로 확인하는 테스트 코드를 만들 수도 있음

**👽 테스트를 하는 이유**
1. 버그를 빨리 잡기 위해
2. 수정이나 리팩터링할 때 기존 기능이 깨지지 않도록 하기 위해
3. 시스템이 어떻게 동작해야 하는지 문서처럼 남기기 위해

**👽 대표적인 테스트 종류**
- 단위테스트, 통합테스트, 시스템테스트, 인수테스트, 회귀테스트 등...
- 일반적으로 테스트 코드를 작성한다면, 단위 + 통합 테스트를 말하는 경우가 많음
  - 개발자가 직접 작성해서 자동화하는 테스트의 대부분이 이 두 가지
  - 테스트 피라미드의 핵심 계층
  - 유지보수, 기능 안전성, 리팩터링 안정성에 가장 큰 기여
  - SpringBoot에서 실제로 개발자들이 가장 많이 만드는 테스트

**👽 단위 테스트(Unit Test)** 
- 전체적인 테스트 전략에서 가장 많이 만들어지는 테스트
- 코드의 가장 작은 단위(하나의 함수나 클래스)가 독립적으로 제대로 작동하는지 확인하는 테스트
  - 예: 더하기 기능, 할인율 계산 기능, 비밀번호 길이가 맞는지 확인하는 기능 등... 아주 작은 로직 검증
- 중요성:
  - 실행 속도가 매우 빠름
  - 작기 때문에 고립된 상태에서 오류 원인을 쉽게 찾을 수 있음
  - 유지 보수가 쉬움
  - 코드 품질을 크게 높임
- 특징:
  - 외부(DB, 네트워크, 파일 등)와 거의 연결하지 않음
  - “순수한 코드 로직”만 검증

> ⭐ 정리: 단위 테스트는 작은 로직을 빠르게 검증

**👽 통합 테스트(Integration Test)**
- 여러 모듈 또는 여러 레이어가 함께 연결되었을 때, 정상적으로 동작하는지 확인하는 테스트
  - 예: 여러 부분이 ‘합쳐진 상태’를 테스트
    - Controller → Service → Repository → DB까지 실제 흐름을 테스트
    - 서비스 로직과 DB가 함께 돌아가는지 확인
    - 외부 API와 연동되는지 확인
- 중요성: 단위 테스트만 하면 “각각은 잘 동작하지만 전체는 안 맞는” 상황이 생기는데, 통합 테스트는 전체 동작을 검사해 문제를 찾아줌.
- 특징:
  - 단: 실행 비용이 큼 (DB, 네트워크, 전체 스프링 컨텍스트 로딩)
  - 단: 속도가 느리고, 환경 설정 필요
  - 장: 실제 사용자와 가장 가까운 환경을 테스트
  - 즉, 현실성은 높지만 비용은 큼

> ⭐ 정리: 통합 테스트는 전체 레이어가 함께 제대로 동작하는지 검증

| 항목     | 단위 테스트          | 통합 테스트           |
| ------ | --------------- | ---------------- |
| 테스트 대상 | 하나의 기능, 하나의 클래스 | 여러 레이어/모듈        |
| 속도     | 매우 빠름           | 느림               |
| 비용     | 낮음              | 높음               |
| 외부 의존성 | 없음 또는 최소        | 실제 DB, 외부 API 포함 |
| 목적     | 개별 로직 검증        | 전체 흐름 검증         |
| 테스트 수  | 많아야 함           | 적당히 필요함          |

> ⭐ 정리: 단위 테스트는 빠르고 많이, 통합 테스트는 적지만 중요한 부분을 검증하면 좋음

**👽 테스트 주도 개발(TDD: Test-Driven Development)**
- 테스트를 먼저 만들고, 그 테스트를 통과하는 코드를 나중에 작성하는 방식(코드를 먼저 짜는 방식과 반대)

**👽 테스트 주도 개발의 흐름**
1. Red ― 테스트 먼저 작성 → 당연히 실패
   - 아직 기능이 없으니 당연히 실패
   - 이 실패는 “내가 무엇을 만들려고 하는가?”를 명확히 함
2. Green ― 테스트를 통과할 최소한의 코드 작성
   - “동작하기만 하면 되는” 가장 단순한 코드를 만들기
   - 과도한 설계를 넣지 않는 이유: 초기부터 복잡하게 만들면 테스트가 어떤 기능을 보장해야 하는지 흐려지기 때문
3. Refactor ― 리팩터링
   - 이 과정에서 기능이 바뀌면 안됌
   - 테스트가 기능을 보장해주기 때문에 변경을 안전하게 수행함
      - 중복 제거
      - 더 읽기 좋은 코드로 개선
      - 메서드 분리
      - 불필요한 조건 정리

**테스트 주도 개발의 효과(장점)**
- 기능 요구사항이 더 명확해짐
- 테스트가 설계를 이끔
- 버그가 줄어듦
- 코드 품질이 일관되고 유지보수가 쉬워짐
- 기능 변경 시 두려움이 줌 (테스트가 보호막 역할)

> ⭐ 정리: 테스트 주도 개발은 “테스트 → 최소 코드 → 리팩터링”의 반복

## 자바에서의 테스트 코드 작성

**👽 자바 테스트에 사용되는 메서드**
1. JUnit 5 기본 어노테이션
  - @Test: “이 메서드는 테스트 메서드다”라고 표시
  - @BeforeEach: 각 테스트 메서드 실행 직전에 매번 호출되는 준비용 메서드
  - @AfterEach: 각 테스트 직후에 호출되는 정리 메서드
  - @BeforeAll / @AfterAll:
    - 전체 테스트 클래스에서 처음 한 번 / 마지막 한 번 실행되는 메서드
    - 보통 공통 자원 초기화/해제에 사용

2. JUnit 5 Assertions (검증용 메서드): 결과가 “기대한 값과 맞는지”를 확인하는 메서드들
  - assertEquals(expected, actual): 두 값이 같은지 검증
  - assertTrue(condition): 조건식이 true인지 검증
  - assertFalse(condition): 조건식이 false인지 검증
  - assertNotNull(object): 조건식이 notnull인지 검증
  - assertThrows(Exception.class, () -> { ... }): 특정 코드를 실행했을 때 예외가 발생해야 하는 경우

3. Mockito 관련 (Service/Controller에서 많이 사용): 테스트에서 진짜 객체 대신 가짜 객체(Stub/Mock)를 사용하는 라이브러리
  - @ExtendWith(MockitoExtension.class): Mockito를 JUnit5와 같이 쓰기 위한 설정
  - @Mock: 가짜 객체 생성 (예: Repository를 진짜 DB 대신 Mock으로 대체)
  - @InjectMocks: Mock들을 주입받을 실제 테스트 대상 클래스 (예: Service)
  - when(mock.method(...)).thenReturn(value): “이 메서드가 호출되면 이런 값을 돌려줘”라고 시나리오 정의
  - verify(mock).method(...): “이 메서드가 실제로 호출됐는지” 검증

4. Spring Boot 테스트 관련: 레이어별로 테스트할 때 자주 쓰는 어노테이션
  - @DataJpaTest:
    - Repository 레이어 테스트용
    - JPA 관련 빈들만 로딩, 인메모리 DB(H2 등) 자동 세팅
  - @SpringBootTest:
    - 통합 테스트용
    - 애플리케이션 전체 컨텍스트를 모두 올려서 테스트
  - @WebMvcTest(ControllerClass.class):
    - Controller 레이어만 테스트할 때 사용
    - 웹 MVC 관련 빈만 로딩, MockMvc로 HTTP 요청 시뮬레이션
  - @MockBean: 
    - Spring 컨텍스트에 등록된 Bean을 Mock으로 교체하는 어노테이션
    - Controller 테스트에서 Service를 Mock 처리할 때 자주 사용

**👽 Repository Layer의 테스트**
- 목표: JPA + DB가 실제로 잘 동작하는지 확인
  - 엔티티 저장/조회 확인
  - Query 메소드 동작 확인
  - Cascade, FetchType, 연관관계가 올바른가
- 사용 기술: @DataJpaTest (인메모리 DB 자동 구성)
- 예:
  ```
  @Test
  void 저장하고_조회된다() {
    // 1) 유저를 만든다
    User user = new User("홍길동", "test@test.com");

    // 2) DB에 저장한다
    userRepository.save(user);

    // 3) 이메일로 다시 조회한다
    User result = userRepository.findByEmail("test@test.com").get();

    // 4) 저장한 값과 같은지 확인
    assertEquals("홍길동", result.getName());
  }
  ```

**Service Layer의 테스트**
- 목표: 비즈니스 로직 검증
  - 입력값 처리 확인
  - 예외 처리 확인
  - 비즈니스 조건(예: 재고 부족, 권한 체크) 확인
- 사용: 
  - Repository를 Mock 객체로 대체
  - DB 접근 없이 서비스 로직만 테스트





**Controller Layer의 테스트**
- 목표: API 요청/응답 형식 검증
  - URL 매핑이 올바른지 확인
  - Request/Response JSON 직렬화 정상인지 확인
  - Validation 동작하는지 확인
- 사용:
  - @WebMvcTest
  - MockMvc로 HTTP 요청 시뮬레이션
