# 3-1. 테스트 코드와 테스트 주도 개발

# 이번 주제

* 테스트와 테스트 주도 개발에 대해 이해합니다.
* 테스트 코드를 작성하고 적용해보는 시간을 가집니다.

# 발표 내용

## 테스트와 테스트 주도 개발

**👽 테스트 ?**
- 내가 만든 코드가 기대한 대로 동작하는지 확인하는 과정
- 사람이 직접 실행해보며 확인할 수도 있고, 컴퓨터가 자동으로 확인하는 테스트 코드를 만들 수도 있음

**👽 테스트를 하는 이유**
1. 버그를 빨리 잡기 위해
2. 수정이나 리팩터링할 때 기존 기능이 깨지지 않도록 하기 위해
3. 시스템이 어떻게 동작해야 하는지 문서처럼 남기기 위해

**👽 대표적인 테스트 종류**
- 단위테스트, 통합테스트, 시스템테스트, 인수테스트, 회귀테스트 등...
- 일반적으로 테스트 코드를 작성한다면, 단위 + 통합 테스트를 말하는 경우가 많음
  - 개발자가 직접 작성해서 자동화하는 테스트의 대부분이 이 두 가지
  - 테스트 피라미드의 핵심 계층
  - 유지보수, 기능 안전성, 리팩터링 안정성에 가장 큰 기여
  - SpringBoot에서 실제로 개발자들이 가장 많이 만드는 테스트

**👽 단위 테스트(Unit Test)** 
- 전체적인 테스트 전략에서 가장 많이 만들어지는 테스트
- 코드의 가장 작은 단위(하나의 함수나 클래스)가 독립적으로 제대로 작동하는지 확인하는 테스트
  - 예: 더하기 기능, 할인율 계산 기능, 비밀번호 길이가 맞는지 확인하는 기능 등... 아주 작은 로직 검증
- 중요성:
  - 실행 속도가 매우 빠름
  - 작기 때문에 고립된 상태에서 오류 원인을 쉽게 찾을 수 있음
  - 유지 보수가 쉬움
  - 코드 품질을 크게 높임
- 특징:
  - 외부(DB, 네트워크, 파일 등)와 거의 연결하지 않음
  - “순수한 코드 로직”만 검증

> ⭐ 정리: 단위 테스트는 작은 로직을 빠르게 검증

**👽 통합 테스트(Integration Test)**
- 여러 모듈 또는 여러 레이어가 함께 연결되었을 때, 정상적으로 동작하는지 확인하는 테스트
  - 예: 여러 부분이 ‘합쳐진 상태’를 테스트
    - Controller → Service → Repository → DB까지 실제 흐름을 테스트
    - 서비스 로직과 DB가 함께 돌아가는지 확인
    - 외부 API와 연동되는지 확인
- 중요성: 단위 테스트만 하면 “각각은 잘 동작하지만 전체는 안 맞는” 상황이 생기는데, 통합 테스트는 전체 동작을 검사해 문제를 찾아줌.
- 특징:
  - 단: 실행 비용이 큼 (DB, 네트워크, 전체 스프링 컨텍스트 로딩)
  - 단: 속도가 느리고, 환경 설정 필요
  - 장: 실제 사용자와 가장 가까운 환경을 테스트
  - 즉, 현실성은 높지만 비용은 큼

> ⭐ 정리: 통합 테스트는 전체 레이어가 함께 제대로 동작하는지 검증

| 항목     | 단위 테스트          | 통합 테스트           |
| ------ | --------------- | ---------------- |
| 테스트 대상 | 하나의 기능, 하나의 클래스 | 여러 레이어/모듈        |
| 속도     | 매우 빠름           | 느림               |
| 비용     | 낮음              | 높음               |
| 외부 의존성 | 없음 또는 최소        | 실제 DB, 외부 API 포함 |
| 목적     | 개별 로직 검증        | 전체 흐름 검증         |
| 테스트 수  | 많아야 함           | 적당히 필요함          |

> ⭐ 정리: 단위 테스트는 빠르고 많이, 통합 테스트는 적지만 중요한 부분을 검증하면 좋음

**👽 테스트 주도 개발(TDD: Test-Driven Development)**
- 테스트를 먼저 만들고, 그 테스트를 통과하는 코드를 나중에 작성하는 방식(코드를 먼저 짜는 방식과 반대)

**👽 테스트 주도 개발의 흐름**
1. Red ― 테스트 먼저 작성 → 당연히 실패
   - 아직 기능이 없으니 당연히 실패
   - 이 실패는 “내가 무엇을 만들려고 하는가?”를 명확히 함
2. Green ― 테스트를 통과할 최소한의 코드 작성
   - “동작하기만 하면 되는” 가장 단순한 코드를 만들기
   - 과도한 설계를 넣지 않는 이유: 초기부터 복잡하게 만들면 테스트가 어떤 기능을 보장해야 하는지 흐려지기 때문
3. Refactor ― 리팩터링
   - 이 과정에서 기능이 바뀌면 안됌
   - 테스트가 기능을 보장해주기 때문에 변경을 안전하게 수행함
      - 중복 제거
      - 더 읽기 좋은 코드로 개선
      - 메서드 분리
      - 불필요한 조건 정리

**테스트 주도 개발의 효과(장점)**
- 기능 요구사항이 더 명확해짐
- 테스트가 설계를 이끔
- 버그가 줄어듦
- 코드 품질이 일관되고 유지보수가 쉬워짐
- 기능 변경 시 두려움이 줌 (테스트가 보호막 역할)

> ⭐ 정리: 테스트 주도 개발은 “테스트 → 최소 코드 → 리팩터링”의 반복

## 자바에서의 테스트 코드 작성

**👽 자바 테스트에 사용되는 메서드**
1. JUnit 5 기본 어노테이션
  - @Test: “이 메서드는 테스트 메서드다”라고 표시
  - @BeforeEach: 각 테스트 메서드 실행 직전에 매번 호출되는 준비용 메서드
  - @AfterEach: 각 테스트 직후에 호출되는 정리 메서드
  - @BeforeAll / @AfterAll:
    - 전체 테스트 클래스에서 처음 한 번 / 마지막 한 번 실행되는 메서드
    - 보통 공통 자원 초기화/해제에 사용

2. JUnit 5 Assertions (검증용 메서드): 결과가 “기대한 값과 맞는지”를 확인하는 메서드들
  - assertEquals(expected, actual): 두 값이 같은지 검증
  - assertTrue(condition): 조건식이 true인지 검증
  - assertFalse(condition): 조건식이 false인지 검증
  - assertNotNull(object): 조건식이 notnull인지 검증
  - assertThrows(Exception.class, () -> { ... }): 특정 코드를 실행했을 때 예외가 발생해야 하는 경우

3. Mockito 관련 (Service/Controller에서 많이 사용): 테스트에서 진짜 객체 대신 가짜 객체(Stub/Mock)를 사용하는 라이브러리
  - @ExtendWith(MockitoExtension.class): Mockito를 JUnit5와 같이 쓰기 위한 설정
  - @Mock: 가짜 객체 생성 (예: Repository를 진짜 DB 대신 Mock으로 대체)
  - @InjectMocks: Mock들을 주입받을 실제 테스트 대상 클래스 (예: Service)
  - when(mock.method(...)).thenReturn(value): “이 메서드가 호출되면 이런 값을 돌려줘”라고 시나리오 정의
  - verify(mock).method(...): “이 메서드가 실제로 호출됐는지” 검증

4. Spring Boot 테스트 관련: 레이어별로 테스트할 때 자주 쓰는 어노테이션
  - @DataJpaTest:
    - Repository 레이어 테스트용
    - JPA 관련 빈들만 로딩, 인메모리 DB(H2 등) 자동 세팅
  - @SpringBootTest:
    - 통합 테스트용
    - 애플리케이션 전체 컨텍스트를 모두 올려서 테스트
  - @WebMvcTest(ControllerClass.class):
    - Controller 레이어만 테스트할 때 사용
    - 웹 MVC 관련 빈만 로딩, MockMvc로 HTTP 요청 시뮬레이션
  - @MockBean: 
    - Spring 컨텍스트에 등록된 Bean을 Mock으로 교체하는 어노테이션
    - Controller 테스트에서 Service를 Mock 처리할 때 자주 사용

**👽 레이어드별 테스트**
- 스프링에서의 역할
  - Controller: HTTP 요청/응답 담당 (URL, JSON, status code)
  - Service: 비즈니스 로직 (규칙, 검증, 흐름)
  - Repository: DB 접근 (JPA, SQL)
- 레이어드별 테스트
  - Repository 테스트: DB + JPA가 제대로 동작하는지 테스트
  - Service 테스트: 비즈니스 규칙이 의도대로인지 테스트
  - Controller 테스트: API 요청/응답이 의도대로인지 테스

**👽 Repository Layer의 테스트**
- DB와 엔티티, JPA 리포지토리가 제대로 동작하는지를 확인하는 테스트
- 비즈니스 로직이 아니라, 데이터 저장·조회 자체를 검증
- 즉, JPA 설정 + 엔티티 매핑 + Repository 인터페이스가 모두 합쳐진 결과를 검증
  - save() 했더니 정말로 DB에 데이터가 들어가는지 확인
  - findById, findByName 같은 쿼리 메서드가 의도한 대로 동작하는지 확인
  - 연관관계 매핑(OneToMany, ManyToOne 등)이 올바른지 확인
  - Cascade, FetchType, Unique 제약조건 등이 기대대로 적용되는지 확인
- Spring 환경에서의 구성:
  1. @DataJpaTest:
    - JPA 관련 컴포넌트만 로딩
    - 인메모리 DB(H2 등)를 자동으로 구성
    - 테스트가 빠르고 가벼움
  2. @Autowired로 Repository 주입
  3. given → when → then 패턴으로 테스트 구조 잡기
- 단계 흐름 예시:
  1. give(준비): 엔티티 객체 생성 (User user = new User("홍길동");)
  2. when(실행):
     - userRepository.save(user);
     - 그리고 findByName("홍길동") 호출
  3. then(확인):
     - 결과가 존재하는지 (isPresent)
     - 필드 값이 예상과 동일한지 (getName()이 "홍길동"인지 등)
- 예시 코드:
  ```
    @DataJpaTest
    class UserRepositoryTest {
    
        @Autowired
        private UserRepository userRepository;
    
        @Test
        void 이름으로_사용자_조회() {
            // given
            User user = new User("홍길동");
            userRepository.save(user);
    
            // when
            Optional<User> result = userRepository.findByName("홍길동");
    
            // then
            assertTrue(result.isPresent());
            assertEquals("홍길동", result.get().getName());
        }
    }
  ```
  - @DataJpaTest로 JPA 테스트 전용 환경
  - Repository를 직접 호출해서 “저장 → 조회” 동작 검증

**👽 Service Layer의 테스트**
- 비즈니스 규칙과 흐름을 검증하는 테스트
- DB가 핵심이 아니라 규칙이 맞냐, 예외 처리가 맞냐가 핵심
  - 예:
    - 이미 존재하는 이름이면 회원 가입 실패
    - 포인트가 부족하면 결제 실패
    - 상태가 CANCELLED인 주문은 수정 금지
- Repository를 Mock으로 사용
  - Service 테스트에서 진짜 DB까지 매번 올라오게 하면, 테스트 속도가 느려지고 “로직 문제”와 “DB 설정 문제”가 섞여서 헷갈림
  - 보통 Service는 실제 객체, Repository는 Mock(가짜) 으로 만듬
  - Mock을 쓰면 Service 로직만 고립해서 테스트 가능
- Service 테스트 구조
  - `@ExtendWith(MockitoExtension.class)` → Mockito + JUnit5 연동 설정
  - `@Mock` : Repository, 외부 API 클라이언트 등
  - `@InjectMocks` : 테스트 대상 Service
  - `when(...).thenReturn(...)` : 특정 상황 정의
  - `assertThrows(...)` : 예외 발생 검증
  - `verify(...)` : 특정 메서드가 호출됐는지 검증
- 예시: “이미 존재하는 이름이면 회원가입이 실패해야 한다”라는 테스트
  1. Repository의 findByName("홍길동")이 항상 Optional.of(이미있는유저)를 돌려주도록 Mock 설정
  2. Service의 register("홍길동") 실행
  3. IllegalArgumentException 같은 예외가 발생해야 함을 검증
- 예시 코드:
  ```
    @ExtendWith(MockitoExtension.class)
    class UserServiceTest {
    
        @Mock
        private UserRepository userRepository;   // 가짜
    
        @InjectMocks
        private UserService userService;         // 실제
    
        @Test
        void 중복_이름이면_예외() {
            // given
            String name = "홍길동";
            when(userRepository.findByName(name))
                    .thenReturn(Optional.of(new User(name)));
    
            // when + then
            assertThrows(IllegalArgumentException.class,
                         () -> userService.register(name));
        }
    }
  ``` 
  - DB는 안 쓰고 Repository 동작만 가짜로 정의
  - Service가 그 상황에서 올바른 판단(예외 발생)을 하는지만 테스트


**👽 Controller Layer의 테스트**
- HTTP 요청/응답 관점에서 API를 검증하는 테스트
- 즉, 실제 클라이언트(브라우저/앱)가 호출하는 것과 최대한 비슷한 환경에서 테스트
- 테스트 내용 예시:
  - URL 매핑이 제대로 되었는지 (예: POST /users)
  - 요청 파라미터, Body(JSON) → Controller 파라미터 매핑이 올바른지
  - Service에 올바르게 위임하는지
  - 응답 status code(200, 400, 404 등)가 맞는지
  - 응답 Body(JSON 구조, 필드 값)가 맞는지
  - Validation 실패 시 올바른 에러 응답을 주는지
- @WebMvcTest + MockMvc 사용
  - `@WebMvcTest(특정Controller.class)`
    - Spring MVC 관련 Bean만 올리고 Service, Repository 등은 자동으로 로딩하지 않음
    - Controller 레이어만 집중 테스트 가능
  - `MockMvc`
    - 실제로 서버를 띄우지 않고도 GET /users, POST /users 같은 HTTP 요청을 흉내 낼 수 있음
    - 응답 status, header, body를 편하게 검증 가능
  - Service는 여기서도 보통 Mock으로 처리
    - Controller 테스트는 “HTTP → Controller 동작”이 주요 관심사고, Service 로직은 이미 Service 테스트에서 검증했으므로...
- Controller 테스트 구성
  - `@WebMvcTest(UserController.class)`
  - `@Autowired MockMvc mockMvc`
  - `@MockBean UserService userService`
  - `mockMvc.perform(요청)`으로 HTTP 호출 흉내
  - `andExpect(status().isOk())`
  - `andExpect(content().string("1"))` 또는 `andExpect(jsonPath("$.name").value("홍길동"))` 등으로 Body 검증
- 예시: “POST /users?name=홍길동 호출 시 200 OK와 id 반환” 테스트
  1. `when(userService.register("홍길동")).thenReturn(1L);` 설정
     - Service가 정상적으로 1L을 주는 상황 가정
  2. `mockMvc.perform(post("/users").param("name", "홍길동"))`
  3. 응답 코드가 200인지 확인
  4. 응답 Body가 `"1"`인지 확인
- 예시 코드:
  ```
    @WebMvcTest(UserController.class)
    class UserControllerTest {
    
        @Autowired
        private MockMvc mockMvc;
    
        @MockBean
        private UserService userService;   // Controller가 사용할 Service를 Mock으로
    
        @Test
        void 사용자_생성_API() throws Exception {
            // given
            when(userService.register("홍길동")).thenReturn(1L);
    
            // when + then
            mockMvc.perform(post("/users")
                            .param("name", "홍길동"))
                   .andExpect(status().isOk())
                   .andExpect(content().string("1"));
        }
    }
  ```
  - `@WebMvcTest` → Controller 테스트 전용 환경
  - Service는 `@MockBean`으로 가짜 주입
  - `MockMvc`로 HTTP 요청 시뮬레이션 + 응답 검증

**👽 Repository, Service, Controller 테스트 비교**
| 레이어        | 무엇을 검증?                           | DB 사용?    | Mock 사용하는 대상       | 대표 어노테이션                              |
| ---------- | --------------------------------- | --------- | ------------------ | ------------------------------------- |
| Repository | JPA 저장/조회, 쿼리, 매핑                 | 예 (H2 등)  | 거의 없음              | `@DataJpaTest`                        |
| Service    | 비즈니스 규칙, 예외 처리                    | 보통 사용 안 함 | Repository, 외부 API | `@ExtendWith(MockitoExtension.class)` |
| Controller | HTTP 요청/응답, URL, JSON, Validation | 보통 사용 안 함 | Service            | `@WebMvcTest`, `MockMvc`              |
