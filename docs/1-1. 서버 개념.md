# 발표 내용

## 서버는 무엇이고 어떻게 동작할까요?, 자바 웹 프레임워크는 어떻게 변화해 왔을까요?

### 1. 서버와 클라이언트는 무엇인가요?

**💀 클라이언트?**
- 웹 브라우저(크롬, 사파리 등), 모바일 앱과 같은 사용자 쪽 프로그램
- 서버에 HTTP **요청(Request)을 보내는 쪽**
    - 예: 로그인 허용 요청, 페이지 URL 요청 등
     
**💀 서버?**
- 클라이언트의 요청을 받아서 처리하고 **응답을 보내는 프로그램**
- 항상 켜져 있으며, 클라이언트의 요청 대기
  - 요청을 받으면 **데이터 조회/로직 수행 → 응답(Response)** 을 생성해서 돌려줌
    
**💀 클라이언트와 서버의 통신**
- 브라우저(클라이언트) ↔ 웹 서버/애플리케이션 서버(서버)
- HTTP/HTTPS 프로토콜로 통신
- 웹 서버
    - Apache, Nginx, IIS 같은 소프트웨어
    - 정적 파일(HTML, CSS, JS, 이미지)을 주로 서빙
- 애플리케이션 서버
    - 비즈니스 로직, DB 연동, 세션 관리 등 “동적인 처리” 담당
    - 자바 쪽에서는 Tomcat, JBoss/WildFly, WebLogic, WebSphere 등

**💀 클라이언트의 요청-서버의 응답 흐름 예시 (HTTP 요청 하나가 오갈 때)**
1. (예) 사용자가 브라우저 주소창에 `https://example.com/users` 입력 후 `Enter`
2. 브라우저가 HTTP 요청을 만들어서 서버 IP/포트로 전송
3. 서버(웹 서버/애플리케이션 서버)가 요청을 받음
4. 서버 안의 애플리케이션 코드(예: 스프링) 흐들
     - URL, HTTP 메서드(GET/POST 등)를 보고 어떤 기능인지 판별
     - DB 조회/비즈니스 로직 처리
     - HTML/JSON 응답 생성
5. 서버가 HTTP 응답을 클라이언트에게 돌려줌
6. 브라우저가 응답을 해석해서 화면에 그림

> ⭐ 정리: 클라이언트는 요청하는 쪽, 서버는 응답을 만들어 주는 쪽

### 2. 자바 웹 프레임워크의 역사

**💀 자바 웹 역사의 4단계**
1. Servlet + JSP 시대 (초기 자바 웹)
2. J2EE / EJB 전성기 (무거운 엔터프라이즈)
3. Struts, Spring 초기 (J2EE 반발 + 경량 프레임워크)
4. Spring 생태계 확장, Spring Boot 시대

**💀 Servlet ?**
  > Oracle Java EE 튜토리얼:
  > 
  > "Servlet은 요청-응답 모델로 접근되는 애플리케이션을 호스팅하는 서버의 기능을 확장하기 위한 자바 클래스이다."
  - 서버 쪽에서 돌아가는 자바 클래스
  - HTTP 요청을 받아서 처리하고, HTTP 응답을 만들어 돌려주는 역할
  - Servlet 이전: 정적 웹 페이지
    - 웹 서버는 그냥 파일 시스템에서 `index.html` 같은 파일을 찾아서 그대로 내려줌
    - 모든 사용자가 똑같은 페이지만 보는 구조
    - 로그인, 게시판, 쇼핑몰처럼 사용자별/상황별 다른 화면을 주기 어려움
  - Servlet 이후: 동적 웹 페이지
    - 사용자 입력 읽기, DB 조회, 비즈니스 로직 수행 가능
    - 그 결과를 HTML 또는 JSON으로 만들어 응답
    - 즉, 로그인, 게시판, 장바구니와 같은 기능이 가능해짐
      
> ⭐ 정리: 정적인 HTML만 주던 웹서버 → 동적 처리 기능

**💀 Servlet의 한계**
- Servlet은 “HTTP 요청 → 자바 코드에서 직접 처리 → 응답 생성” 정도만 제공
- 하지만 실무에서는 아래 것들이 필요
    - 트랜잭션 관리(Commit/Rollback)
    - DB 커넥션 풀 관리
    - 보안 (권한 체크)
    - 분산 환경 지원(RMI, EJB)
    - 스레드 관리(멀티스레딩)
    - 세션 클러스터링
    - 메시징(JMS)
    - 대규모 애플리케이션 구조화
- 이 모든 것을 개발자가 직접 구현해야 했으며, 회사마다 구현 방식도 제각각
 
**💀 표준의 필요성 대두**
- 2000년대 초반, 기업 시스템의 거대화
    - 수만 명 고객이 접속
    - 수십 개 서버가 분산 환경으로 동작
    - 트랜잭션(계좌, 주문)이 매우 중요
    - 보안 규칙이 복잡
    - 특정 서버 벤더(WebLogic, WebSphere)에 종속되면 비용이 폭발
- **자바 진영 전체을 위한 엔터프라이즈 표준 사양 필요**

**💀 J2EE(JavaEE) 등장**
- Sun Microsystems에서 제작
- 이름 변화: J2EE(Java 2 Platform, Enterprise Edition) → 이후 Java EE, 지금은 Jakarta EE
- 대규모 기업용 시스템(엔터프라이즈 애플리케이션)을 만들기 위한 **규격서(표준 스펙 묶음)**
    - Servlet, JSP
    - **EJB (Enterprise JavaBeans)**
    - JMS(메시징)
    - JPA(영속성)
    - JTA(트랜잭션) 등등 포함
- 어떠한 벤더를 사용하더라도 같은 방식으로 개발하는 것이 목표
- 기업 시스템을 만들 때 필요한 기능을 자바 표준으로 통합하려고 함

**💀 EJB(Enterprise JavaBeans) 등장**
- Servlet 기반 개발 시 비즈니스 로직과 인프라 로직의 혼합
  - 규모가 커지면 유지보수 불가능
  - 구현 방식이 제각각이라 재사용 불가능
- EJB = 비즈니스 로직을 담는 컴포넌트
  - 트랜잭션 처리
  - 보안
  - 분산 호출(Remote)
  - 스레드 관리
  - 라이프사이클 관리
  - 로깅
  - 예외 처리 패턴
  - 자원 관리 등 자동 지원
- 개발자는 비즈니스 로직만 POJO처럼 만들고, 나머지 엔터프라이즈 지능은 EJB 컨테이너가 자동으로 처리
  - POJO: 특별한 규칙·상속·프레임워크 의존 없이, **순수한 자바** 문법만으로 만든 일반 객체
    - 비즈니스 로직과 프레임워크 의존성 분리
    - 유지보수, 테스트 자동화 쉬워짐
      
> ⭐ 정리: Servlet → J2EE/EJB가 등장한 이유
>
> 1. Servlet만으로는 엔터프라이즈급 기능 부족
>    - 트랜잭션, 보안, 분산 처리, 스레드 관리 직접 구현해야 함
> 2. 기업 환경에서 필요한 기술 요구가 급격히 증가
>    - 수많은 서버, 대규모 트래픽, 빠른 개발 속도 필요
> 3. 아키텍처가 표준화되지 않아 프로젝트마다 구조가 제각각
>    - 표준 엔터프라이즈 모델 필요 → J2EE 스펙 등장
> 4. 비즈니스 로직에만 집중하고 싶음
>    - 나머지는 서버 컨테이너가 알아서 처리해주길 원함 → 그 역할을 하는 것이 EJB 컨테이너


**💀 J2EE/EJB의 문제점**
1. 구조가 너무 복잡
   - 인터페이스, 구현 클래스, 홈 인터페이스, 원격 인터페이스…
   - 시스템 부팅, 배포, 설정이 무겁고 복잡
2. 컨테이너 종속적
   - 특정 앱 서버(WebLogic, WebSphere 등)에 종속되는 경우 많음
3. 개발/테스트 속도가 느림
    - 간단한 기능을 만들고 돌려보려 해도, 앱 서버 띄우기 → 배포 → 다시 빌드…
4. POJO가 아님
   - EJB 규칙을 따르는 특수한 컴포넌트여서, 단위 테스트하기 어려움
   - 순수한 자바 객체처럼 자유도가 떨어짐
> ⭐ 정리: 기능 자체는 훌륭하지마, 필요 이상으로 복잡한 구조와 규칙을 요구함. (Too much)


**💀 Spring Framework 등장**
- Rod Johnson의 문제의식
  - J2EE/EJB 기반 프로젝트를 하면서 너무 무겁고 비효율적이라는 결론에 도달
  - 본인이 쓰던 대체용 프레임워크 코드 ~30,000줄 정도를 책과 함께 공개
- 이 코드가 발전한 것이 바로 **Spring Framework 1.0**
  > “Spring 스토리는 2001년에 시작되었고, J2EE 프로젝트에서 겪은 문제를 해결하기 위해 설계되었다.”

## Spring Framework의 주요 특징은 무엇인가요? 그리고 그 특징이 어떻게 구현될 수 있었을까요?

**💀 Spring의 목표**
1. POJO 기반
   - 특수한 컨테이너 전용 컴포넌트(EJB)가 아니라 평범한 자바 객체로 비즈니스 로직 작성
2. IoC/DI 컨테이너
   - 객체 생성/연결을 컨테이너가 관리 → 애플리케이션 구조 단순화
3. 선택적 EJB 사용
   - EJB를 “안 써도 되고, 쓰더라도 선택지 중 하나”로 만들자
4. AOP로 트랜잭션/보안 등 공통 기능 처리
   - EJB 컨테이너가 제공하던 트랜잭션, 보안 기능을 AOP+DI 기반으로 구현
5. 구체 구현에 덜 묶이는 설계
   - JDBC, ORM, JTA, JMS 등을 유연하게 사용하기 위해
> ⭐ 정리: J2EE/EJB가 제공하던 좋은 개념(트랜잭션, 보안, 컴포넌트화)은 살리고, 너무 무겁고 복잡한 부분은 버린 경량 대안을 만들자
>
> - 복잡한 인프라 코드가 비즈니스 로직을 방해함 → AOP 필요
>
> - 객체들의 의존성이 너무 강함 → DI 필요
>
> - 객체 생성/연결/수명 관리를 개발자가 일일이 함 → IoC 컨테이너 필요

**💀 DI(Dependency Injection, 의존성 주입) 필요**
- 기존 방식의 문제점
  - OrderService가 OrderRepository를 강하게 직접 생성 → 결합도가 강함
  - 테스트할 때 mock 객체로 바꿀 수 없음
  - 코드 변경이 많아짐
  - 서비스 간 의존 관계가 덩어리처럼 엉킴
- DI = 객체가 필요로 하는 의존 객체를 스스로 만들지 않고, 외부에서 주입받는 것
  - 생성은 Spring이 하고, "사용"만 개발자가 함

**💀 DI 효과**
- 결합도 감소 → 유지보수 쉬움
- 테스트 용이 → mock 주입 가능
- 애플리케이션 구조가 단순해짐
- 객체 생명주기를 중앙에서 관리 가능

  ⇒ 이로 인해 스프링 전체 아키텍처가 강해짐.

**💀 IoC(Inversion of Control, 제어의 역전) 필요**
- 기존 자바 애플리케이션의 문제점
  - 객체 생성(new), 의존성 연결, 초기화, 소멸 → 이 모든 것을 개발자가 직접 관리
  - 규모가 커지면 객체 수가 수백, 수천 개가 되고, 관리가 불가능
- IoC = 객체의 생성·관리·연결에 대한 제어권이 개발자 → 프레임워크로 넘어가는 것
  - 개발자는 객체가 “어떻게” 만들어지는지 신경 쓰지 않음
  - 스프링이 대신 객체를 만들고 연결
- DI가 “의존성 자체를 주입해준다”라면, IoC는 “그 의존성을 누가 관리하느냐에 대한 제어권”

**💀 AOP(Aspect Oriented Programming, 관점 지향 프로그래밍) 필요**
- 실무 서비스 매서드는, 트랜잭션 시작/종료 → 권한 체크 → 로깅 → 예외 처리의 반복
  - 이것이 중복적으로 수백 개의 매서드에 퍼지면 "횡단 관심사(Cross-Cutting Concern)” 발생
    - 서비스 로직이 흐트러짐
    - 유지보수 불가
    - 로깅/보안 정책 변경 시 전부 수정해야 함
- AOP = 공통 로직(트랜잭션, 보안, 로깅)을 한 곳에 모아 관리하고, 특정 메서드가 실행될 때 자동으로 끼워 넣는 기술
  - 서비스 코드는 핵심 로직만 남기고, 반복되는 공통 로직은 AOP로 처리한다.
 
> ⭐ 정리: Spring의 주요 특징
>
> 1. DI(의존성 외부 주입): 클래스 간 결합도 감소, 테스트 용이
> 2. IoC(제어권 역전): 객체 생성/관리 중심화 필요
> 3. AOP(공통 기능 분리): 로깅/트랜잭션/보안 중복 제거


## Spring은 무엇일까요? 또, Spring과 SpringBoot의 주요한 차이점은 뭘까요?

**💀 Spring ?**
- 애플리케이션 전체(객체 생성, 의존성, 트랜잭션, 웹 요청 처리 등)를 관리해주는 **‘자바 기반 애플리케이션 프레임워크'**
- EJB의 겨울이 끝나고, 개발자에게 봄(Spring)이 왔다는 상징적 의미

**💀 Spring이 제공하는 기능**
1. Core Container (DI/IoC)
   - 객체 생성과 의존성을 관리
   - 스프링의 심장부(ApplicationContext)
2. AOP / Infrastructure(트랜잭션, 보안 등)
   - 공통 기능을 AOP로 적용
   - 보안/트랜잭션 기능을 프레임워크 차원에서 적용
3. Web 계층(Spring MVC, WebFlux)
   - HTTP 요청을 받아 MVC 패턴으로 처리
   - Controller · Service · Repository 구조 제공

> ⭐ 정리: Spring은 기업용 애플리케이션 전체 구조를 통째로 관리하는 **인프라 프레임워크**

**💀 Spring 구성요소**
- 크게 6개의 큰 덩어리(Module Group)로 구성
- 각 덩어리 안에 여러 세부 모듈(JAR 라이브러리)이 포함
1. Core Container (스프링의 심장, IoC/DI 기능)
2. AOP (관점 지향 프로그래밍)
3. Data Access / Integration (JDBC, ORM, 트랜잭션)
4. Web Layer (Spring MVC 포함)
5. Messaging
6. Testing

**💀 1. Core Container (코어 컨테이너)**
- 스프링의 핵심: IoC/DI를 담당
- 포함 모듈
  - spring-core
    - 스프링의 가장 기초 유틸 기능을 제공(리소스 처리 등)
  - spring-beans
    - Bean 정의, 생성, 의존성 주입(DI) 처리 → ApplicationContext가 사용하는 핵심 엔진
  - spring-context
    - “스프링 컨테이너(ApplicationContext)” 구현
      - Bean 관리
      - 이벤트 발행
      - 국제화 기능
      - 환경(Environment) 설정
  - spring-expression(SpEL)
    - `@Value("#{1 + 1}")` 같은 표현식 처리 기능

> ⭐ 정리: Core Container는 Spring의 IoC/DI 기능을 담당하는 엔진으로, Spring의 모든 기능은 Core Container 위에서 돌아간다.

**💀 2. AOP (Aspect-Oriented Programming)**
- 공통 기능(트랜잭션·보안·로그)을 분리해서 적용하는 기능
- 포함 모듈
  - spring-aop
    - 프록시 기반 AOP 구현(JDK Dynamic Proxy, CGLIB)
  - spring-aspects
    - @AspectJ 스타일 AOP 지원

> ⭐ 정리: AOP는 Spring이 트랜잭션/보안/로그 같은 공통 기능을 “코드에 흩뿌리지 않고 한 곳에서 관리”할 수 있게 한다.

**💀 3. Data Access / Integration (데이터 접근 계층)**
- JDBC, ORM, 트랜잭션 등 DB 관련 기능
- 포함 모듈
  - spring-jdbc
    - JdbcTemplate 제공 → 반복되는 JDBC 코드를 획기적으로 줄임
  - spring-orm
    - Hibernate, JPA 같은 ORM과 스프링 연동
  - spring-tx
    - 트랜잭션 선언적 관리(@Transactional)
  - spring-oxm
    - XML ↔ 객체 매핑
  - spring-jms
    - 메시징(JMS) 연동

> ⭐ 정리: Spring은 JDBC, ORM, 트랜잭션을 일관된 프로그래밍 모델로 제공한다.

**💀 4. Web Layer (웹 계층)**
- Spring MVC를 포함한 웹 기능
- 포함 모듈
  - spring-web
    - HTTP 요청/응답 처리, 멀티파트 파일 업로드 등 기본 웹 기능
  - spring-webmvc
    - Controller, ViewResolver, HandlerMapping, DispatcherServlet 등 전통적인 MVC 웹 개발 핵심
  - spring-websocket
    - 웹소켓 지원
  - spring-webflux
    - 비동기·논블로킹 WebFlux 프레임워크 (리액티브)

> ⭐ 정리: Web 모듈은 HTTP 기반 애플리케이션(SPG, REST API)을 만들 때 사용된다. **Spring MVC는 그중 가장 중요한 핵심 구성요소**

**💀 5. Messaging**
- 메시징 기반 아키텍처 기능
- 포함 모듈
  - spring-messaging
    - STOMP/WebSocket 메시징 처리
    - 메시지 컨버터

**💀 6. Testing**
- 스프링 통합 테스트 지원
- 포함 모듈
  - spring-test
    - ApplicationContext 로딩
    - 가짜 MVC(MockMvc) 테스트
    - JUnit 연동

> ⭐ 정리: Spring은 Core Container + AOP + Data + Web 기능을 모두 갖춘 종합 엔터프라이즈 애플리케이션 프레임워크

**💀 MVC 패턴의 필요**
- 초기 Servlet/JSP 방식의 문제
  - 하나의 Servlet 안에, 비즈니스 로직 + 화면 생성(HTML) + 데이터 처리가 다 섞임
  - 유지보수 어려움
  - 화면 바뀌면 비즈니스 로직도 건드려야 하고, 비즈니스 로직 바꾸면 화면도 깨짐
- 역할을 분리해서 서로 간섭하지 않도록 하기 위해 MVC 패턴 등장

**💀 MVC 패턴 ?**
- M(Model) - V(View) - C(Controller)
- 역할별로 명확하게 분리하는 패턴
- Model
  - 데이터, 비즈니스 로직 결과
  - DB에서 가져온 정보, 서비스 로직 결과 등
- View
  - 화면 출력 담당(HTML, Thymeleaf, JSON 등)
  - “어떤 모양으로 보여줄지”만 관여
- Controller
  - 사용자의 요청을 받고 어떤 서비스 로직을 실행할지, 어떤 View를 선택할지 결정

> ⭐ 정리:
>
> “Controller는 흐름 제어, Model은 데이터, View는 화면”
>
> 이 3개의 책임을 분리해 유지보수성을 극대화한 패턴

**💀 Spring MVC 패턴의 동작 과정**
- **DispatcherServlet(Front Controller)**을 중심으로 전체를 연결
1. 클라이언트가 HTTP 요청 전송
2. 톰캣(Tomcat) 같은 서블릿 컨테이너가 요청을 받음
3. 톰캣이 이 요청을 DispatcherServlet에게 전달
   - DispatcherServlet이 “모든 요청을 처리하는 서블릿”으로 등록되어 있으므로
4. DispatcherServlet → HandlerMapping에게 물어봄
   - 예: “이 URL은 어떤 Controller가 처리해야 하지?”
5. 스프링은 해당 Controller 메서드를 찾아줌
6. DispatcherServlet → Controller 호출
7. Controller → Service → Repository 로직 수행
8. Controller가 결과(Model)를 반환
   - 예: `{“username”: “hyunji”}`)
9. DispatcherServlet → `ViewResolver`에게 “이 결과를 어떤 View로 렌더링해야 하지?”를 물어봄
10. 결정된 View가 HTML, JSON, JSP 등을 생성하여 클라이언트에게 응답

> ⭐ 정리: Spring MVC는 “Front Controller” 방식으로 DispatcherServlet이 모든 요청 흐름을 조율하는 MVC 프레임워크

**💀 SpringBoot ?**
- 스프링을 쉽게 쓰기 위한 기술
- 스프링을 편하게 실행하고 설정할 수 있도록 만든 도구(런타임 패키지 + 자동 설정 엔진)
- 즉, 스프링은 “프레임워크”, 스프링 부트는 “실행 플랫폼 + 설정 자동화 도구”

**💀 SpringBoot의 필요성**
- 순수 스프링은 설정이 많음(XML/Java Config)
  - 톰캣 설치 필요
  - 의존성 하나하나 직접 추가
  - web.xml 등록, DispatcherServlet 직접 설정
  - 실행환경 구성 복잡
- 즉, 스프링 자체는 매우 유연하지만, 직접 설정할 게 너무 많았다. → Spring 설정을 해결하기 위해 SpringBoot 등장

**💀 SpringBoot의 기능**
1. AutoConfiguration (자동 설정)
   - 스프링 부트는 프로젝트에 포함된 라이브러리를 보고 적절한 스프링 설정을 자동으로 구성
   - 개발자는 Controller만 만들면 API가 동작함
2. Starter 의존성
   - 스프링 부트는 관련 라이브러리를 묶어서 제공
   - 의존성 충돌, 버전 지옥 해결.
3. 내장 서버 제공 (Embedded Tomcat)
   - 과거 스프링: WAR 파일 만들어서 설치형 WAS(WebLogic/Tomcat 등)에 배포해야 했음
   - 스프링 부트:
     - 내장 톰캣 포함
     - java -jar app.jar 하면 서버가 바로 뜸
   - DevOps, 클라우드 시대에 최적화된 구조

**💀 Spring과 Spring Boot의 주요한 차이점**
| 항목    | Spring             | Spring Boot    |
| ----- | ------------------ | -------------- |
| 설정    | XML/Java Config 직접 | 자동 설정 제공       |
| 서버    | 외장 톰캣 설치           | 내장 톰캣 포함       |
| 의존성   | 개발자가 직접 관리         | Starter로 자동 구성 |
| 실행    | WAR 배포             | JAR 실행         |
| 구조    | 유연하지만 복잡           | 빠르고 단순         |
| 개발 속도 | 느림                 | 빠름             |


> ⭐ 정리:
>
> - Spring MVC: MVC 패턴을 기반으로 DispatcherServlet이 요청 흐름을 조율하는 웹 프레임워크.
>
> - Spring: IoC/DI/AOP/Web/Data 기능을 제공하는 엔터프라이즈 프레임워크.
>
> - Spring Boot: Spring을 더 쉽게, 더 빠르게, 자동으로 설정해주는 실행 플랫폼.


## Servlet Container와 DispatcherServlet, Application Context(Spring Container)는 무엇인가요? 그리고 어떻게 동작하나요?

**💀 Servlet Container ?**
- 톰캣(Tomcat), 제티(Jetty) 등과 같은 서버
- HTTP 요청을 받아서, 알맞은 Servlet 객체를 찾아 실행해 주는 프로그램(서버)
    - HTTP 요청 수신 (소켓 열고 포트에서 대기)
    - Servlet 객체의 생명주기 관리 (생성, 초기화, 요청 처리, 종료)
    - 요청마다 스레드 생성 및 관리
    - Filter, Listener 등 실행

> ⭐ 정리: Servlet Container는 톰캣 같은 서버이며, 네트워크 통신과 서블릿의 생명주기를 관리하면서, 요청을 대신 서블릿에게 전달해 주는 실행 환경

**💀 Servlet Container의 사용자의 요청 처리: HTTP 요청이 들어왔을 때의 실제 흐름**
- 요청은 항상 Servlet Container → Servlet 흐름으로 간다
- 스프링을 쓰든 안 쓰든, 맨 앞에는 항상 Servlet Container가 있음
1. 클라이언트(브라우저)가 `http://example.com:8080/hello` 로 요청 전송
2. OS → 해당 포트(8080)를 듣고 있는 톰캣(Servlet Container)에게 전달
3. 톰캣은 URL과 매핑 정보를 보고 “/hello는 어떤 Servlet이 처리해야 하지?” 를 확인
4. 해당 Servlet 인스턴스를 찾거나(없으면 새로 생성 후 init() 호출) 그 Servlet의 service() 메서드를 요청 스레드에서 호출
5. Servlet은 doGet/doPost에서 비즈니스 로직 수행 후 응답 작성
6. 톰캣이 응답을 HTTP Response로 포장해서 클라이언트에 전송

**💀 DispatcherServlet ?**
- 스프링 MVC의 핵심 Servlet
- 톰캣 입장에서는 Servlet 중 하나
- 모든 HTTP 요청을 한 군데에서 받아서 어떤 컨트롤러(Controller)가 처리할지 “배분”

> ⭐ 정리: DispatcherServlet은 Spring MVC의 입구이자, 모든 요청을 가로채서 컨트롤러에게 전달하는 프론트 컨트롤러 역할의 서블릿

**💀 Front Controller 패턴**
- 이전 구조의 문제 상황
  - URL마다 서블릿을 하나씩 만들고, 공통 로직(로그인 체크, 로깅, 예외 처리 등)이 각 서블릿에 중복
  - 변경이 생기면 모든 서블릿 코드 수정
