# 발표 내용

## 데이터베이스는 무엇이고 어떤 종류가 있나요? 또, 관계형 데이터베이스란 무엇인가요?

**👽 데이터베이스의 필요성**
- 많은 데이터를 안전하게 저장, 조회, 수정, 삭제하기 위해
- 동시성 제어, 트랜잭션 보장, 영속 저장, 대규모 데이터 처리를 안정적으로 수행

> ⭐ 정리: 데이터베이스란, 많은 데이터를 안전하고, 빠르고 일관성있게 저장, 조회, 수정, 삭제할 수 있게 만든 전문 시스템

**👽 데이터베이스의 종류**
1. 관계형 데이터베이스(RDBMS)
2. NoSQL 데이터 베이스

**👽 관계형 데이터베이스(RDBMS)**
- 예: MySQL, PostgreSQL, Oracle, SQL Server
- 테이블 구조: 행과 열(row and column)
- 스키마 기반: 각 테이블의 구조(컬럼 이름, 타입 등)가 미리 정의
- SQL 이라는 표준 언어로 조회/저장/수정/삭제
- 트랜잭션, 무결성, 참조 관계 지원이 매우 강력

**👽 NoSQL 데이터 베이스**
- 스키마가 유연하거나, 대규모 분산 시스템을 위해 등장한 DB
- 유연한 구조
- 비정형 데이터에 강함
- 문서 (Document) DB
   - 예: MongoDB
   - JSON과 비슷한 문서 형태로 저장
   - 컬렉션 안에 문서들이 들어있는 구조
- 키-값(Key-Value) DB
   - 예: Redis
   - Key와 Value의 단순 매핑
   - 캐시, 세션과 같은 간단하고 빠른 저장용
- Wide-Column/Column Family DB
   - 예: Cassandra, HBase
   - 컬럼 단위 저장에 최적화
   - 아주 많은 데이터 처리에 강함
- 그래프 DB
   - 예: Neo4j
   - 노드와 간선으로 관계 표현

**👽 관계형 데이터 베이스 ?**
- 데이터를 테이블 단위로 관리
   - 엑셀 표와 비슷...
- 테이블을 PK-FK 관계로 연결
   - PK(Primary Key): 각 행을 유일하게 구분하는 값
   - FK(Foreign Key): 다른 테이블의 PK를 참조하는 값
- 테이블 간의 연결 = 관계(Relation) ⇒ **관계형 데이터베이스**

**👽 관계형 데이터베이스 특징**
- 정합성(ACID)을 강하게 보장
- SQL 기반으로 명확한 구조 유지

**👽 ERD(Entity Relationship Diagram) ?**
- 여러 테이블이 서로 관계를 맺어 복잡한 구조를 가지면, 관리 힘듬 → ERD 등장
- 데이터베이스 구조를 시각적으로 표현하는 다이어그램
- Entity와 그 사이의 관계(Relationship)을 그림으로 표현한 데이터베이스 설계도
- DB 설계 도면
- 개발자들이 같은 구조를 공유하기 좋음
- 실제 테이블 생성, Entity 클래스 설계, 연관관계 매필 설계 가능

**👽 ERD(Entity Relationship Diagram)의 구성요소**
1. Entity(엔티티)
2. Attribute(속성)
3. Relationship(1:1, 1:N, N:M등 관계)
4. Cardinality(키디널리티, 관계 수)

**👽 Entity(엔티티)**
- 실제 DB의 테이블
- ERD에서 네모박스로 표현
- 예: Member, Order, Product 등

**👽 Attribute(속성)**
- Entity가 가진 Column들
- ERD에서 타원으로 표현하여 연결
- 예: Member의 id, name, email 등
- 특수 속성
- PK(Primary Key, 기본키): Entity의 대표 키
- FK(Foreign Key, 외래키): 다른 Entity 참조

**👽 Relationship(관계)**
- 엔티티끼리 어떻게 연결되어 있는지 표시
- ERD에서 선으로 엔티티를 연결하고, 중간에 1, N 등 관계 수(카디널리티)를 나타냄
- 예: Member 1 --- N Order , 한 명의 회원은 여러 개의 주문을 할 수 있다.

**👽 Cardinality(카디널리티, 관계 수)**
- 1 : 1
- 1 : N
- N : M

> ⭐ 정리:
>
> 데이터 보관의 필요성 → "데이터베이스" 등장
>
> 구조적 데이터 + 안정적인 트랜잭션 → "관계형 데이터베이스" 채택
>
> 관계형 데이터베이스는 테이블, PK/FK, 관계로 구성 → 이 구조를 그림으로 시각화 "ERD"
>
> ERD의 기본요소: Entity(엔티티), Attribute(속성), Relationship(관계) 

## ORM은 무엇일까요? 스프링에서 ORM을 어떻게 이용할 수 있을까요?

**👽 자바와 DB의 모델 불일치(객체-관계 불일치)**
- 우리가 만드는 코드 대부분은 객체 지향 언어(예: Java)
  - **객체**를 사용
- 반면, DB는 **테이블**로 데이터 저장
- 자바는 객체(필드, 메서드, 상속, 캡슐화), DB는 테이블(행, 열, FK, 조인) → 모델 불일치
- 문제: SQL을 직접 작성하여 컬럼 하나하나 값을 객체에 수동으로 입력
  - 컬럼 이름 실수, 타입 실수 발생 증가
  - 동일한 코드 패턴이 서비스마다 반복
- 해결: **ORM(Object-Relational Mapping)**

**👽 ORM(Object-Relational Mapping) ?**
- 객체 관계형 매핑 (객체OOP - 관계RDB)
- 객체와 관계형 데이터베이스 테이블을 자동으로 매핑해 주는 기술 또는 프레임워크
  - Member 클래스 ↔ member 테이블
  - member.getName() ↔ member.name 컬럼
  - member.getOrders() ↔ orders 테이블과의 FK 관계
- ORM이 대신 해주는 것들
  - 엔티티 → insert/update/delete용 SQL 자동 생성
  - 쿼리 결과 → 엔티티 객체 자동 매핑
  - 연관관계(1:N, N:1) → join + 객체 그래프 조립

**👽 ORM의 필요성**
1. SQL/ResultSet/PreparedStatement 반복 코드를 줄임
2. 비즈니스 로직을 객체 모델 기준으로 생각할 수 있음
3. DB 벤더(MySQL, PostgreSQL 등) 변경 시 비교적 덜 의존적
4. 캐시, 변경 감지(Dirty Checking), 지연 로딩(Lazy Loading) 등 부가 기능
   - 변경 감지(Dirty Checking, 더티 체킹): 트랜잭션 안에서 엔티티의 값이 변경되면, JPA가 자동으로 UPDATE SQL을 생성하는 기능. 수정 쿼리를 직접 작성하지 않아도 알아서 DB에 반영해주는 기능.
   - 캐시(1차 캐시): 영속성 컨텍스트 내부에서 엔티티를 저장해두고 재사용하는 메모리 저장소. 트랜잭션 안에서 같은 데이터를 두 번 조회하면 DB가 아니라 캐시(메모리)에서 가져오기 때문에 빠르고 효율적. 실제로는 한 번만 DB 조회하고 두 번째는 캐시에서 가져옴.
   	> ⭐ 정리:
   	>
   	> Dirty Checking: 엔티티 값을 바꾸면 JPA가 자동으로 UPDATE SQL을 만들어주는 기능
   	>
   	> 1차 캐시: 같은 엔티티를 다시 조회할 때 DB가 아니라 메모리에서 꺼내주는 기능
- 아주 복잡한 쿼리, 성능 튜닝 시에는 JPQL/Native SQL이 여전히 필요하지만, 전체 코드 베이스 중 대부분은 ORM이 자동 생성하는 SQL로 커버 가능

**👽 스프링에서의 ORM 활용 방식**
1. Entity(자바 객체) ↔ 테이블(DB) 매핑
2. Repository(인터페이스) ↔ SQL 자동 생성/실행
3. Service에서 객체만 다루고 SQL은 전혀 등장하지 않음
- 객체 중심으로 개발한다면, JPA + Hibernate + Spring Data JPA가 SQL 처리와 매핑 작업을 전부 자동으로 함
	- JPA: 자바 개발자가 객체 지향적으로 데이터베이스를 다룰 수 있도록 돕는 표준화된 기술
		- 객체-관계 매핑
		- 복잡한 sql 작성 없이 객체 관점에서 데이터를 조작하고 관리해줌

**👽 Spring Data JPA**
- 문제: JPA만 사용한다면, 엔티티 메니저를 직접 다뤄야 함
- 해결: Spring Data JPA를 사용하여 인터페이스만 만들어도 여러 구현을 자동으로 생성해 줌
  - 반복되는 DB 접근 로직이 사라짐
  - 개발자는 비즈니스 로직에 집중
  - 테스트 작성도 훨씬 쉬워짐

**👽 Spring Data JPA의 역할**
- CRUD 구현체 자동 생성
- 메서드 이름 기반 쿼리 자동 생성
- 페이징/정렬 자동 처리
- @Query로 JPQL 작성 지원
- 트랜잭션 관리 스프링과 자동 통합

> ⭐ 정리:
>
> JPA를 훨씬 더 쉽게 사용하게 도와주는 스프링 기술
1. 기본 CRUD 기능 (CrudRepository 기능 포함)
   - 저장 / 수정
     - 새 엔티티이면 INSERT
     - 기존 엔티티이면 UPDATE
     - 여러 개 한 번에 저장 가능
   - 단건 조회
   - 전체 조회
   - 삭제

2. 페이징 & 정렬 (PagingAndSortingRepository 기능 포함)
   - 페이징 조회
   - 정렬 조회

3. 메서드 이름 기반 쿼리 자동 생성
   - 메서드 이름만 만들어도 Spring Data JPA가 쿼리를 자동 생성 함

4. @Query를 이용한 직접 JPQL 작성
   - 복잡한 조건을 인터페이스에서 직접 정의 가능

5. 쿼리 힌트 제공
   - 성능 최적화용 설정 가능

6. Flushing 기능
   - JPA 영속성 컨텍스트를 강제로 데이터베이스와 동기화 가능

7. Batch 관련 기능
   - 한 번에 삭제/저장하는 배치 기능 제공

- 전체 기능 요약

| 기능           | 설명                                             |
| ------------ | ---------------------------------------------- |
| CRUD         | save, findById, findAll, delete, count, exists |
| 페이징          | findAll(Pageable pageable)                     |
| 정렬           | findAll(Sort sort)                             |
| 메서드 쿼리 자동 생성 | findBy…, readBy…, countBy…, existsBy…          |
| @Query       | JPQL 또는 Native SQL 직접 작성                       |
| Proxy 반환     | getReferenceById()                             |
| Batch 작업     | deleteInBatch(), deleteAllInBatch()            |
| Flush        | flush(), saveAndFlush()                        |

> ⭐ 정리: JpaRepository = “DB CRUD + 페이징/정렬 + 자동 쿼리 생성 + JPQL 작성 기능”을 전부 제공하는 스프링 데이터 JPA의 핵심 인터페이스


## Entity는 무엇이고 생명주기는 어떻게 되나요? 관련 어노테이션은 무엇이 있을까요?

**👽 Entity ?**
- JPA가 관리하는 데이터베이스 테이블에 매핑되는 객체
	- DB의 member 테이블 ↔ 자바의 Member 클래스
	- DB의 order 테이블 ↔ Order 클래스
	- 이렇게 객체 세계와 데이터베이스 세계를 연결해주는 핵심 단위

> ⭐ 정리: Entity = DB 테이블을 객체처럼 다루기 위한 JPA의 핵심 클래스

**👽 영속성(Persistence): JPA에서의 영속성**
- 엔티티 객체가 JPA의 ‘영속성 컨텍스트’에서 관리되는 상태 
- 단순한 새로운 개체가 아닌, JPA가 이 객체를 자동으로 추적하며 DB와 연동하는 상태

**👽 영속성 컨텍스트(Persistence Context)**
- 엔티티 객체를 저장해두고 관리하는 1차 캐시 같은 저장소
- JPA가 제공하는 컨테이너로 중요한 기능 수행
	- 엔티티의 변경사항을 추적(Dirty Checking)
	- 필요한 순간에 SQL 실행
	- 같은 엔티티는 1차 캐시에서 재사용 (반복 쿼리 방지)
	- 지연 로딩(Lazy Loading) 동작
	- 트랜잭션 범위 내에서 엔티티들을 일관되게 관리

**👽 영속성의 중요성**
- 영속 상태 = JPA가 엔티티를 “관리하겠다”는 뜻
- 여러 장점을 자동으로 얻음
	1.	변경 감지(Dirty Checking)
		- 세터로 값을 바꾸면 → JPA가 변경을 감지 → 트랜잭션 종료 시 UPDATE SQL 자동 생성
	2.	1차 캐시 활용
		- 이미 조회한 엔티티를 또 조회하면 DB 조회가 아니라 캐시에서 반환
	3.	지연 로딩(Lazy Loading)
		- 연관된 엔티티를 실제로 필요할 때까지 조회를 미룸
	4.	동일성 보장
		- 동일한 트랜잭션 안에서는 같은 엔티티는 항상 “하나의 객체”로 보장됨

**👽 Entity의 생명 주기**
- JPA는 ENtity를 4가지 상태로 나눠 관리한다.
1. 비영속(Transient)
2. 영속(Persistence)
3. 준영속(Detached)
4. 삭제(Removed)

**👽 비영속(Transient)**
- 단순히 new로 만든 상태
- JPA와 전혀 관계없음 (관리 대상 X)

**👽 영속(Persistence)**
- EntityManager.persist() 또는 repository.save()를 호출하면 엔티티가 영속성 컨텍스트에 저장되어 관리되는 상태
- 이때 DB에 바로 insert되지 않아도 됨
- 트랜잭션 종료 시점에 쿼리가 나갈 수 있음(쓰기 지연)

**👽 준영속(Detached)**
- 영속 상태였다가 관리 대상에서 빠진 상태
- 트랜잭션이 종료되면 대부분 준영속이 됨
- em.detach(), clear(), close() 등을 호출해도 준영속이 됨
- 준영속 엔티티는 더 이상 변경 감지 등이 일어나지 않음

**👽 삭제(Removed)**
- 삭제 명령을 받은 상태
- 트랜잭션이 끝나면 DELETE SQL 실행

> ⭐ 정리: 전체 생명주기의 흐름
>
> new → (save/persist) → 영속(persistent)
>
> 영속 → (delete/remove) → 삭제(removed)
>
> 영속 → (clear/detach/transaction 종료) → 준영속(detached)


**👽 어노테이션 ?**
- 코드에 붙이는 특별한 메모(정보)
- 스프링이나 JPA 같은 프레임워크에게 이 코드를 어떻게 처리해야 하는지 알려주는 표시
- 덕분에 우리가 직접 SQL, 매핑코드를 쓰지 않아도 됨
- 예: 자바에서...
	- @Entity → DB 엔티티다
	- @Service → 서비스 계층이다
	- @Transactional → 트랜잭션을 걸어라
	- @Repository → 예외 변환 기능을 적용해라

**👽 어노테이션의 필요성**
- 코드를 깔끔하게 만들기 위해
	- 설정을 코드 위에 바로 표시 → 읽기 쉬움
- 반복적인 작업을 자동화
	- 객체 생성, 매핑, 검증, 트랜잭션 등 자동 처리
- 프레임워크에서 필요한 정보를 전달하기 위해


**👽 Entity에 관련된 어노테이션: JPA가 제공하는 기본 어노테이션 4가지**
1. 엔티티 자체를 위한 어노테이션
	- @Entity
		- 이 클래스가 엔티티임을 선언하는 가장 핵심 어노테이션
	- @Table(name = “table_name”)
		- 매핑할 테이블 이름 지정 (생략하면 클래스 이름 사용)
2. 필드 매핑을 위한 어노테이션
	- @Id
		- PK 지정
	- @GeneratedValue
		- PK 자동 생성
			- IDENTITY(MySQL)
			- SEQUENCE(Oracle)
			- AUTO(자동 선택)
	- @Column
		- 컬럼 이름/길이/nullable 설정
	- @Enumerated(EnumType.STRING)
		- Enum 저장방식 선택 (STRING 권장)
	- @Lob
		- 대용량 데이터 (TEXT/BLOB)
	- @Transient	
		- DB에 저장하지 않을 필드
3. 연관관계 매핑 어노테이션
	- @ManyToOne
		- N:1 관계 (가장 자주 사용)
	- @OneToMany
		- 1:N 관계
	- @OneToOne
		- 1:1 관계
	- @ManyToMany
		- N:M 관계 (실무에서는 지양)
	- @JoinColumn(name = “컬럼명”)
		-FK 매핑
	- @JoinTable
		- N:M 관계에서 중간 테이블 정의할 때 사용
4. 값 타입을 위한 어노테이션
	- @Embeddable
		- 값 타입 클래스 정의
	- @Embedded
		- 엔티티 안에 값 타입 포함

> ⭐ 전체 정리: 
>
> Entity = 데이터베이스 테이블을 객체로 표현한 것
>
> 영속성 = Entity가 JPA의 영속성 컨텍스트에서관리되는 상태
> 
> Entity 생명주기 = 비영속 > 영속 > 준영속 > 삭제


## 연관관계 매핑은 무엇이고 어떻게 이용할 수 있을까요?

**👽 연관관계 매핑 ?**
- 엔티티들 사이의 관계(1:N, N:1 등)를 객체(필드/참조)와 DB(FK/조인) 둘 다 맞춰서 표현하는 것
	- DB 쪽: member 테이블, order 테이블, 그리고 order.member_id 같은 FK
	- Java 객체 쪽: Order 안에 Member member; 같은 필드
	- 연관관계 매핑: 이 두 개를 어노테이션(@ManyToOne, @OneToMany, @JoinColumn 등)으로 연결

**👽 연관관계 매핑의 필요성**
- 문제: DB는 FK, 객체는 “참조”를 사용
	- 객체는 연관된 객체에 바로 접근하고 싶지만, DB에서는 전부 FK + JOIN으로 표현 함
	- FK를 직접 숫자로 들고 다니는 대신 참조(객체)를 쓰고, 그 참조가 DB의 FK와 잘 맞도록 하는 것이 필요
- 해결: 연관관계 매핑을 사용하여 객체답게 코딩 가능
	- FK 숫자 대신, 실제 연결된 객체를 쓰도록 함

**👽 연관관계 매핑의 종류**
1. 방향: 단방향/양방향
2. 다중성(관계 수): 1:1, 1:N, N:1, N:M

**👽 방향: 단방향/양방향**
- 단방향: 한쪽 방향에서만 참조하는 관계
- 양방향: 양쪽에서 서로 참조하는 관계
	- 연관 관계의 주인은 FK(외래키)를 가진 쪽

| 종류  | 설명                            |
| --- | ----------------------------- |
| 단방향 | 한쪽만 참조, 가장 단순하고 많이 씀          |
| 양방향 | 양쪽 모두 참조, 필요할 때만 사용, 주인 개념 필요 |


**👽 다중성(관계 수): 1:1, 1:N, N:1, N:M**
- 1:1(OneToOne)
	- 둘 중 한 쪽에 FK가 들어감
- 1:N(OneToMany)
	- N:1의 반대 방향
	- FK 위치 문제로 비효율적(정말 필요할 때만 사용하는 것을 추천)
- N:1(ManyToOne) 
	- 가장 흔한 관계
	- 데이터베이스에서 FK가 걸리는 쪽(N)이 연관관계의 주인
- N:M(MAnyToMany)
	- 유지보수 어려움
	- 중간 엔티티를 만들어 1:N + N:1로 풀어쓰는 것을 추천

| 관계  | 어노테이션       | 특징                 |
| --- | ----------- | ------------------ |
| N:1 | @ManyToOne  | 가장 많이 사용됨, FK 가진 쪽 |
| 1:N | @OneToMany  | 양방향의 반대편에서 많이 사용   |
| 1:1 | @OneToOne   | 드물지만 명확한 구조에서 사용   |
| N:M | @ManyToMany | 실무 비추, 중간 엔티티로 해결  |

> ⭐ 정리:
> 
> N:1 단방향이 가장 기본. 연관관계의 주인은 항상 N
> 
> 1:N 단방향은 지양. 양방향은 옵션(필요할 때만 추가). N:M은 비추(중간 엔티티 추가하기)


**👽 영속성 전이(Cascade) ?**
- 부모 엔티티에 수행한 영속성 작업(저장/삭제,PERSIST/REMOVE 등)을 자식 엔티티에게도 자동으로 전파하는 기능
	- 부모 하나만 저장했는데 자식도 함께 저장
	- 부모 하나만 삭제했는데 자식도 함께 삭제
	- 이런 자동 처리를 해주는 옵션 = 영속성 전이(Cascade)

**👽 영속성 전이(Cascade)의 필요성**
- 여러 엔티티를 별도로 저장/삭제(persist/remove) 할 필요 없음
- 부모 중심으로 엔티티 생명주기를 관리 가능
- 코드 간단, 실수 방지

**👽 영속성 전이(Cascade)의 종류**

| 타입          | 설명                        |
| ----------- | ------------------------- |
| **PERSIST** | 저장 전파                     |
| **REMOVE**  | 삭제 전파                     |
| **ALL**     | PERSIST + REMOVE 포함 전체 전파 |
| MERGE       | 병합 전파                     |
| REFRESH     | 다시 읽기 전파                  |
| DETACH      | 준영속 전파                    |

- PERSIST, REMOVE, ALL(주로 사용)
	- 대부분 ALL 사용
- MERGE, REFRESH, DETACH(특수 상황)

**👽 영속성 전이(Cascade)의 활용**
- 사용하는 경우: 부모 없이는 자식이 존재할 수 없는 강한 종속 관계 (즉, Parent → Child 관계)
	- 자식은 오직 부모와 함께 생성/삭제됨
	- 생명주기가 거의 동일함
	- 자식이 다른 부모에게 공유되지 않음 (예: OrderItem은 다른 Order에 속할 수 없음)
- 사용하지 않는 경우: 여러 엔티티가 “공유”하는 엔티티에는 쓰지 않음
	- 공유 관계로 연결된 엔티티에 영속성 전이를 사용한다면, 의도하지 않은 것 까지 삭제되거나 할 수 있음
