# 발표 내용

## 다양한 로그인 기법

**👽 세션(Session) 방식**
- 서버가 로그인한 사용자의 정보를 서버 메모리나 DB(Session Store)에 저장하고, 클라이언트에는 Session ID를 쿠키로 전달해 식별하는 방식
- 사용자가 인증에 성공하면 서버가 “세션 데이터”를 서버 쪽 저장소에 보관하고, 클라이언트에는 그 세션을 식별하기 위한 세션 ID 값만 전달해서 이후 요청마다 그 ID로 사용자를 구분하는 방식
- 서버는 세션 ID와 연결된 내부 저장소를 통해 “현재 사용자 상태”를 알아냄 → 상태 유지(Stateful) 방식
- 특징:
  - 세션 데이터는 보통 서버 메모리, DB, Redis 같은 세션 저장소에 저장
  - 클라이언트는 주로 쿠키에 세션 ID를 담아 자동 전송
  - 세션에는 사용자 ID, 권한, 로그인 시간, 기타 상태 정보가 들어갈 수 있음
  - 서버가 세션을 삭제하거나 만료시키면, 해당 세션 ID는 더 이상 유효하지 않
- 장점:
  - 보안 제어가 서버 중심:
    - 세션 데이터가 서버에 있어서, 서버가 직접 세션을 무효화하거나 수정할 수 있음
    - 문제 발생 시 특정 세션만 골라서 강제 로그아웃 처리 가능
  - 세밀한 상태 관리: 사용자별 상태(언어 설정, 장바구니, 권한 변경 등)를 서버에서 세밀하게 관리 가능
  - 토큰 노출 시 영향 최소화 가능: 세션 ID가 유출되더라도, 서버에서 해당 세션을 바로 삭제하면 위험을 빠르게 차단할 수 있
- 단점:
  - 확장성(Scalability) 문제:
    - 서버가 모든 사용자 세션 상태를 가지고 있어야 하므로, 접속자 수가 증가할수록 세션 저장소 부담이 커짐
    - 서버 여러 대(멀티 인스턴스, 로드밸런싱) 환경에서는 세션 공유(공통 세션 저장소) 또는 Sticky Session(특정 서버에 고정 라우팅)
같은 추가 구성이 필요
  - 상태 유지 비용: 상태를 유지하는 만큼 메모리/스토리지 비용이 증가
  - 다양한 클라이언트·마이크로서비스 환경에서 불편: 서버가 상태를 갖고 있어야 하므로, 완전한 Stateless 아키텍처에는 부적합

**👽 토큰(Token) 방식**
- 사용자가 인증에 성공하면 서버가 토큰(Access Token 등)을 생성하여 클라이언트에 전달
- 이후 요청마다 클라이언트가 토큰을 함께 보내고, 서버는 그 토큰을 검증해서 사용자 식별
- 토큰 내부에 필요한 정보를 담으면, 서버가 별도의 세션 저장을 하지 않아도  → 무상태(Stateless) 방식 지향
- 특징:
  - 토큰은 일반적으로 서명(Signature) 을 포함해 위·변조 여부를 확인할 수 있음
  - 토큰에는 사용자 식별자, 만료 시간, 권한 정보 등 클레임(Claims) 을 포함(대표적으로 JWT)
  - 서버는 토큰이 유효한지만 확인하고, 추가로 상태를 저장하지 않아도 인증·인가를 수행할 수 있음
  - 토큰은 보통 HTTP 헤더(Authorization 등) 에 담아 전송
- 장점:
  - 서버 무상태(Stateless)에 가까운 구조:
    - 각 요청이 토큰만으로 인증·인가를 수행하므로, 서버가 세션 상태를 유지할 필요 없음
    - 서버 인스턴스를 수평 확장하기 쉬워지고, 로드밸런싱 설계가 단순
  - 다양한 클라이언트와 연동 용이:
    - 웹, 모바일, 다른 서비스, 마이크로서비스 간 통신 등에서 동일한 토큰을 재사용 가능
    - API 기반, 마이크로서비스 아키텍처에 적합
  - 중앙 세션 저장소 불필요(이론상): 순수한 Access Token 검증만으로는 DB/세션 저장소 조회 없이 처리 가능
- 단점:
  - 토큰 탈취 시 위험:
    - 토큰이 노출되면, 만료 시간까지 공격자가 사용자의 권한을 그대로 사용할 수 있음
    - 서버가 상태를 저장하지 않으면, 이미 발급된 토큰을 “즉시” 무효화하기가 어려움
  - 강제 로그아웃/권한 변경 반영이 어려움:
    - 토큰이 Self-contained(자체 정보 포함)인 경우, 발급 시점의 정보가 고정
    - 사용자의 권한이 바뀌거나, 강제 로그아웃을 시켜야 할 때, 기존 토큰을 강제로 모두 무효화하려면, 블랙리스트 관리, 토큰 버전 필드 관리 등 추가 메커니즘이 필요
  - 토큰 크기 증가에 따른 비용: JWT처럼 정보를 많이 담을수록 토큰 길이가 길어져, 네트워크 전송량 증가, HTTP 헤더 크기 증가 등의 오버헤드 발생
  - 보안 관리 책임이 클라이언트에 더 많이 전가: 토큰은 클라이언트에 저장되므로, 저장 위치 및 전송 방식(쿠키/Storage/Native 저장소 등)을 적절하게 보호해야 

> ⭐ 정리:
>
> 세션 방식: “서버가 상태를 들고 있어 관리·보안은 쉽지만, 확장과 분산 환경에서는 부담이 큰 방식”
>
> 토큰 방식: “서버는 가볍고 확장에 유리하지만, 토큰 탈취/무효화/관리 문제를 설계로 해결해야 하는 방식”


## JWT란 무엇인가요?

**👽 JWT ?**
- JWT(JSON Web Token)는 클라이언트와 서버 간 인증·인가를 위해 사용되는 자체 포함(Self-contained) 토큰 형식
- 문자열 형태
- 특징: Header.Payload.Signature 의 3부분으로 이루어짐
  - Header: 어떤 알고리즘으로 서명했는지 등 메타 정보
  - Payload: 사용자 정보(Claims), 토큰 만료 시간 등의 데이터
  - Signature: 위·변조 검사용 서명(Signature)
- 작동 방식:
  - 서버는 사용자 인증에 성공하면 JWT를 서명하여 발급
  - 클라이언트는 요청마다 JWT를 포함해 보내고,
  - 서버는 토큰 검증만으로 사용자 식별을 수행 (Stateless)

> 📎참고: Self-contained 의미
>
> JWT 자체에 필요한 정보가 포함되어 있으므로, 서버가 세션 저장소를 유지하지 않아도 인증을 처리할 수 있음

**👽 토큰 종류**
- Access Token:
  - 인증이 필요한 API 요청 시 사용되는 토큰
  - 보통 짧은 수명을 가짐
  - 탈취 위험을 줄이기 위해 만료가 빠르도록 설계
- Refresh Token:
  - Access Token이 만료되었을 때 새로운 Access Token을 발급하는 용도
  - 긴 수명을 가지며, 서버가 관리하는 것이 일반적
- Opaque Token:
  - 내용이 보이지 않는 “불투명한” 토큰
  - 내부 정보를 포함하지 않으므로, 서버가 저장해두고 조회해야 인증 가능
  - 위·변조 걱정 없이 단순 토큰 ID로 사용 가능
- JWT(JSON Web Token):
  - Header/Payload/Signature 구조의 Self-contained Token
  - 토큰 자체에 정보를 담아 서버 상태 저장을 최소화 가능
- Signed Token: 서명만 되어 있고 내용은 누구나 읽을 수 있음(JWT 대부분)
- Encrypted Token: 내용 자체를 암호화하여 보호
- 일반적 JWT는 서명만 되어 있을 뿐 비밀이 아님 > 민감 정보 저장 금지

**👽 Spring에서 JWT 생성 방식**
-대표 JWT 라이브러리: 
  - io.jsonwebtoken.Jwts (JJWT 라이브러리)
  - com.auth0.jwt.JWT (auth0 java-jwt)
- JWT 생성 절차:
  - 시크릿 키(HMAC) 또는 공개키/개인키(RSA) 기반으로 서명하여 생성
  1. 서명 키 준비
     - HMAC 방식(공유 키) 또는 RSA 방식(비대칭 키) 중 선택
     - 서버는 이 키로 JWT 생성 및 검증 수행
  2. Header 설정
     - 어떤 알고리즘으로 서명할지 지정(HMAC-SHA256 등)
  3. Payload 구성
     - 필수 값: sub(사용자 ID 등), exp(만료 시간)
     - 선택 값: 역할(Role), 사용자 정보 등 Claims
  4. Signature 생성
     - Header + Payload를 서명 알고리즘으로 암호학적으로 서명
  5. Header.Payload.Signature 형태로 직렬화하여 문자열 토큰으로 만듦

**👽 JWT 문제점**
1. 탈취 후 악용 가능 (가장 큰 문제)
   - JWT는 발급 후 서버가 상태를 가지지 않는 구조
   - 즉 이미 발급된 JWT를 서버가 임의로 “즉시” 무효화할 수 없음
   - 탈취되면 만료될 때까지 악용 가능
   - 세션 방식의 강제 로그아웃처럼 즉각 차단이 어렵다
2. Payload는 암호화되지 않음
   - JWT는 기본적으로 Base64URL 인코딩일 뿐이며 암호화되어 있지 않음
   - 누구나 디코딩하여 Payload 내용을 읽을 수 있어, 민감 정보(전화번호, 이메일, 개인정보 등) 를 절대 넣으면 안 됨
   - 서명은 위·변조만 방지할 뿐, Payload의 노출을 막지 않음
3. Self-contained 특성으로 인한 정보 갱신 문제
   - JWT는 발급 시점의 정보를 그대로 포함하므로, 사용자의 권한(Role) 변경, 계정 정지와 같은 상태 변화가 즉시 반영되지 않음
   - 정보 변경을 반영하려면 토큰 재발급, 토큰 버전 필드 관리, 블랙리스트와 같은 복잡한 추가 로직이 필요
4. 토큰 크기가 큼
   - 세션 ID보다 훨씬 큰 문자열 구조
   - Payload에 클레임이 많으면 크기가 급격히 커짐
   - 결과적으로 요청 헤더 증가, 네트워크 비용 증가, 대량 요청 시 서버 과부하 가능성 증가
5. 만료 전 서버 무효화가 어려움
   - Stateless 특성 때문에 “토큰 폐기”라는 개념이 기본적으로 없음
   - 이를 보완하기 위해 Refresh Token 관리, 블랙리스트 저장, Token Rotation 등을 추가해야 함
6. Refresh Token 누수 시 장기 피해 가능
   - Refresh Token의 수명이 긴 만큼, 탈취 시 영향 기간이 김
   - Refresh Token Rotation 같은 보완 기법을 반드시 고려해야 함

## AccessToken, RefreshToken

**👽 RefreshToken의 등장 이유**
- Access Token은 탈취 위험 때문에 짧게 유지해야 함
- 그러나 너무 짧으면 사용자 경험이 나빠짐 → 긴 수명 Refresh Token으로 Access Token을 재발급하도록 설계

**👽 Refresh Token 구현**
- DB 또는 Redis에 저장하여 관리
- 사용자와 매핑해 저장하면 Refresh Token 탈취 시 즉시 폐기 가능
- Access Token 만료 시 Refresh Token을 이용해 새로운 Access Token 발급

**👽 Refresh Token 장단점**
- 장점:
  - Access Token 수명을 짧게 유지해 보안 향상
  - 탈취 시 피해를 최소화
  - 서버는 Refresh Token만 관리하면 됨
- 단점:
  - Refresh Token 탈취 자체는 여전히 위험
  - Refresh Token 저장소(DB/Redis) 운영 필요 → 완전한 무상태 아님

**👽 RTT(Refresh Token Rotation) ?**
- Refresh Token을 재발급할 때마다 이전 Refresh Token을 폐기하고 새로운 토큰으로 교체하는 방식
- 장점:
  - 탈취된 Refresh Token이 사용되면 사용 즉시 탐지 가능
  - 보안성이 크게 높아짐
- 단점:
  - 서버가 Refresh Token 상태를 계속 기록해야 함
  - 구현 복잡도 증가


**1. RefreshToke이 탄생한 이유
2. RefreshToken의 구현
3. RefreshToken의 장단점
  
   1. RTT(Refresh Token Rotation)**

## Spring Security란 무엇인가요?

**👽 인증(Authentication)과 인가(Authorization)**

| 개념                 | 의미                       |
| ------------------ | ------------------------ |
| 인증(Authentication) | "누구인지 확인" (로그인 절차)       |
| 인가(Authorization)  | "무엇을 할 수 있는지 확인" (권한 체크) |

**👽 Spring Security의 구조**
- SecurityFilterChain: Spring Security의 핵심. 모든 요청은 필터를 통과함
- AuthenticationManager: 인증 처리 핵심 컴포넌트
- AuthenticationProvider: 실제 인증 로직을 수행
- UserDetailsService: 사용자 조회
- PasswordEncoder: 비밀번호 검증
- AccessDecisionManager: 인가 처리

**👽 Spring Security 작동 흐름**
- SecurityFilter → 인증(Authentication) → 인가(Authorization) → Controller 실행
1. 요청이 들어오면 SecurityFilterChain 통과
2. 인증이 필요한 URL → 인증 필터가 토큰/세션 검사
3. 인증 정보 없음 → AuthenticationManager로 인증 시도
4. Provider가 UserDetailsService로 사용자 조회
5. 성공 시 SecurityContext에 Authentication 저장
6. 이후 인가 필터에서 권한(Role) 검사
7. Controller 접근 허용/거부 결정

2. Spring Security의 구조
3. Spring Security의 작동 흐름**
