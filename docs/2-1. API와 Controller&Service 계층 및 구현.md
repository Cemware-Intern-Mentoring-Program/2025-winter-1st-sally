## API는 무엇이고 왜 사용할까요? 또, API를 문서화 하는 방법은 무엇이 있을까요?

**👽 API ?**
- 프로그램끼리 대화할 때 쓰는 규칙(약속) 세트
- 프로그램끼리 API라는 약속을 정하고, 그 규칙에 맞춰 데이터를 주고받음

**👽 API 필요성**
1. 프론트/백엔드 분리
   - 프론트는 화면에만 집중
   - 백엔드는 데이터/비즈니스 로직에 집중
   - 둘은 API라는 약속만 맞추면 됨
2. 시스템 간 연동
   - 예1: 우리 서비스 ↔ 결제 서비스(카카오페이, 네이버페이)
   - 예2: 우리 서비스 ↔ 외부 인증(카카오 로그인, 구글 로그인)
   - 이런 것도 다 API로 통신
3. 재사용
   - 같은 API를 웹, 모바일, 다른 내부 시스템에서도 같이 사용 가능
4. 보안 / 통제
   - 어떤 기능을 외부에 열지, 어떤 데이터만 보여줄지, API 레벨에서 제어 가능

**👽 API 명세서 ?**
- API에 대한 약속을 정리해 둔 설명서
- 프론트 개발자, 백엔드 개발자, QA, 외부 업체 등이 해당 API를 어떻게 쓰면 되는지 보고 이해할 수 있도록 저장한 문서

**👽 API 명세서의 내용**
1. 기본 정보
2. URL & Method
3. 요청 데이터(Request)
4. 응답 데이터(Response)
5. 에러 케이스

**👽 API 명세를 위한 도구**
1. 문서 작성 도구 (사람이 직접 쓰는 방식)
2. API 테스트 + 공유 도구
3. 코드 기반 자동 문서화 도구 (Swagger / OpenAPI 계열)

**👽 문서 작성 도구 (사람이 직접 쓰는 방식)**
- 종류: 
   - Word, Google Docs
   - Notion
   - Confluence
   - Markdown + Git 저장소
- 장점:
  - 자유도가 높음
  - 회사 위키랑 같이 쓰기 좋음
- 단점:
   - API가 바뀔 때마다 수동으로 수정해야 해서 실제 코드와 문서가 쉽게 틀어짐

**👽 API 테스트 + 공유 도구**
- Postman: API를 실제로 요청 보내서 테스트하는 도구
  - 여러 API를 묶어서 컬렉션으로 관리
  - 각 API에 설명, 예시, 샘플 저장 가능
    - 간단한 API 문서처럼도 활용 가능
- 장점
  - 개발 중에 바로바로 테스트하기 좋음
  - 팀끼리 컬렉션 공유 쉽고, 환경 변수 세팅 편함
- 단점
  - “정식 문서”보다는 “테스트용 스펙”에 가깝고 Swagger처럼 코드에서 자동 생성되는 문서는 아님

**👽 코드 기반 자동 문서화 도구 (Swagger/OpenAPI 계열)**
- OpenAPI: REST API 명세를 위한 표준 포맷(스펙) 이름
- Swagger: 이 OpenAPI 스펙을 만들고 보여주는 대표적인 툴/라이브러리 이름
- Spring에서 많이 쓰는 방식:
  - springdoc-openapi 라이브러리 추가
  - Controller 메소드에 간단한 어노테이션 달기
     - 자동으로 API 문서 + 웹 UI 생성 (예: /swagger-ui.html, /swagger-ui/index.html로 접속)
- 장점:
  - 코드와 문서가 같이 관리됨 (= 코드 바꾸면 문서도 자동 반영)
  - 브라우저에서 바로 API 설명 + 테스트 가능
- 단점
  - 초기 셋업이 필요
  - 간단한 프로젝트에는 오버킬일 수 있음

> 📎 참고: Springfox vs Springdoc
>
> Springfox
> - 예전에 많이 쓰던 Swagger 연동 라이브러리
> - Spring Boot 3 이후로는 거의 안 씀 (호환 문제 많음)
> 
> Springdoc (springdoc-openapi)
> - 최근 스프링에서 Swagger/OpenAPI 쓰면 대부분 이거 사용
> - Spring Boot 3, Spring 6과 잘 맞음
> - “Spring에서 Swagger 쓸 거야” 하면 Springdoc을 쓴다고 이해


## REST API는 뭘까요? RESTful한 설계는 무엇일까요?

**👽 REST API**
- 자원을 어떻게(HTTP 방식) 다룰지 정해놓은 표준적인 방식 
- 인터넷에서 자료를 다루는 규칙 세트
- URL(주소)을 ‘자원(Resource)’처럼 다루고, HTTP 규칙을 이용해 통신하는 방식
  - 인터넷 주소(URL)은 자원(resource)를 나타냄
  - HTTP 메서드(GET, POST, PUT, DELETE)는 행동(동작)을 나타냄
  - JSON 같은 포맷은 자원의 표현(Representation) 을 의미함

**👽 REST의 핵심 원칙**
1. URL은 자원을 표현함
   - URL에는 “동사”가 들어가지 않는 것이 원칙
   - 예: /getUserInfo ❌ → /users/1 ⭕ (“조회"는 GET 메서드가 이미 표현하고 있기 때문)
2. 무상태성(Stateless)
   - 요청마다 필요한 정보를 모두 포함해야 함
   - 서버는 이전 요청 상태 기억 안 함
3. 표현(Representation)
   - 응답은 JSON, XML 등으로 표현됨
   - 요즘은 JSON이 거의 표준

> ⭐️ 정리:
>
> REST API = URL은 자원을 나타내고, 메서드는 동작을 나타내고, 응답은 JSON으로 주고, 서버는 상태를 기억하지 않고 독립적으로 처리하는 방식으로 통신하는 API

**👽 RESTful한 설계 ?**
- REST 철학을 잘 반영한 설계
1. URL은 자원(명사)만 사용하기
   - 동작은 URL이 아니라 HTTP 메서드가 표현하기 때문
2. 응답코드를 정확하게 사용하기
   | 상태코드             | 의미      |
   | ---------------- | ------- |
   | 200 OK           | 정상 조회   |
   | 201 Created      | 정상 생성   |
   | 400 Bad Request  | 잘못된 요청  |
   | 404 Not Found    | 자원 없음   |
   | 401 Unauthorized | 인증 안됨   |
   | 403 Forbidden    | 접근권한 없음 |
   | 500 Server Error | 서버 오류   |
3. 일관된 구조 유지하기
   - 계속 같은 규칙으로 확장 가능해야 RESTful함
4. 자원 간 관계를 URL로 명확하게 표현하기
5. 서버는 상태를 기억하지 않음(Stateless)
   - 각 요청은 완전 독립적이어야 함
6. JSON 기반 메시지 표준화
   - 요즘 RESTful API에서 거의 필수:
   - 공통 응답형태
   - 에러 응답 표준

**👽 REST API vs RESTful 설계 요약**

| 구분 | REST API               | RESTful 설계                          |
| -- | ---------------------- | ----------------------------------- |
| 의미 | REST 원칙에 맞게 만든 API     | REST 철학을 깊이 반영한 “잘 만든” API          |
| 목적 | 통신 방식(형식)              | 일관성·표준성·가독성·확장성                     |
| 예  | GET/POST/PUT/DELETE 사용 | URL 규칙, 응답코드, 자원 표현, 무상태성 등을 완전히 준수 |

- REST API는 “형식”
- RESTful 설계는 “철학 + 베스트 프랙티스”

> ⭐️ 정리:
>
> REST API란?
> - URL(자원) + HTTP 메서드(행위)로 통신하는 방식
> - JSON 응답, 무상태성 등의 원칙 포함
> 
> RESTful 설계란?
> - REST 원칙을 제대로 지킨 깔끔한 설계
> - 예측 가능하고 일관성 있고 확장가능한 API를 만드는 것


## 객체의 직렬화와 역직렬화는 무엇이고 **@RequestBody**과 @ModelAttribute의 값 매핑은 어떻게 이뤄지나요?

**👽 직렬화(Serialization)**
- 객체 → 문자열/바이트(JSON 등)로 바꾸는 과정
- 네트워크로 보내거나, 파일에 저장하려면, “문자열/바이트” 형태여야 함
- 예: User 객체를 JSON으로 보내야 할 때
  - `{ "id": 1, "name": "홍길동" }`

**👽 역직렬화(Deserialization)**
- 문자열/바이트(JSON 등) → 객체로 바꾸는 과정
- 예: 클라이언트가 JSON을 보내면: `{ "id": 1, "name": "홍길동" }` → 서버에서 다시 자바 객체로 되살림: `User user = ...` 


**👽 컨트롤러 매개변수에 아무 어노테이션도 없으면?**
- 스프링이 자동 규칙에 따라 값을 어디서 읽어올지 결정함
1. 단순 타입(String, 숫자 등)은 @RequestParam처럼 자동 처리
   - 단순 타입 = 스프링이 값 하나만 주면 되는 타입들
      - 예: String, int, long, double, boolean, Integer, Long, …
   - 요청 파라미터(Query/Form)에서 읽어옴
2. 객체 타입(클래스)은 @ModelAttribute처럼 자동 처리
  - 객체(POJO) → 요청 파라미터를 필드에 바인딩해서 객체 생성
  - 즉, 요청 파라미터를 객체의 필드에 매핑함
3. JSON Body는 자동으로 안 읽음
  - JSON을 읽으려면 반드시 @RequestBody 붙여야 함

| 타입             | 어노테이션 없다면 00 역할           | 값을 가져오는 곳             | JSON Body 읽음 유무 |
| -------------- | ------------------ | ----------------------- | ------------- |
| String/int 등   | @RequestParam 역할   | Query/Form 파라미터         | ❌             |
| 사용자 객체(User 등) | @ModelAttribute 역할 | Query/Form 파라미터 → 필드 매핑 | ❌             |


> ⭐️ 정리:
>
> 어노테이션 없으면 스프링은 모든 값을 "요청 파라미터"로 취급
>
> JSON Body를 쓰고 싶으면 반드시 @RequestBody가 필요



**👽 스프링에서 객체의 직렬화 · 역직렬화 담당 ?**
- 스프링 MVC는 요청 데이터를 읽어서 객체로 바꾸고(역직렬화), 객체를 응답으로 보낼 때 다시 JSON 같은 문자열로 바꾸는(직렬화) 과정을 자동으로 함
- Jackson의 `ObjectMapper`가 핵심 담당

**👽 ObjectMapper의 작동방식**
1. JSON → 객체 (역직렬화)
   1. JSON 문자열을 분석
   2. “이 key는 어떤 값인지, 어떤 타입인지”를 파악
   3. 자바 클래스의 필드 이름과 비교해 매칭
   4. 리플렉션을 이용해 그 클래스의 객체를 만들고 각 필드에 알맞은 타입으로 값을 채워 넣음
   - 외부에서 온 JSON을 “자바 객체로 복원하는 역할
2. 객체 → JSON 문자열(직렬화)
   1. 자바 객체를 읽음
   2. 필드들의 이름과 값을 꺼냄
   3. 이를 JSON 형식으로 변환해서 문자열로 만듬
   - 자바 객체를 네트워크로 보낼 수 있는 텍스트 형태로 변환하는 역할

> ⭐ 정리:
> ObjectMapper
> - JSON 문자열 ↔ 자바 객체 변환 담당
> - 스프링에서 자동으로 사용됨


**👽 @RequestBody와 @ModelAttribute의 공통점 및 차이점**
- 공통점: 요청 데이터를 자바 객체로 변환함
- 차이점: 데이터를 읽는 장소, 데이터를 매핑하는 방식이 다름

**👽 @RequestBody ?**
- 데이터 위치: HTTP Body(요청 본문)에서 데이터를 읽음
- 동작 방식: Body 안의 JSON을 그대로 가져와 ObjectMapper를 이용해 JSON → 객체로 변환
- 특징: JSON처럼 “본문 중심”의 데이터를 처리할 때 사용 (REST API에서 가장 많이 쓰는 방식)

> ⭐ 정리: @RequestBody는 Body(JSON)를 ObjectMapper로 읽어서 객체 생성

**👽 @ModelAttribute ?**
- 데이터 위치:
  - QueryString / Form 파라미터에서 값을 읽음
  - 즉, key=value 형태의 요청 데이터 처리
- 동작 방식: 요청에 포함된 파라미터 이름들을 수집하고, 객체의 필드 이름과 맞춰서 스프링의 바인더(WebDataBinder)가 필드에 값을 넣어줌
- 특징: 화면에서 폼(form) 입력이 넘어오는 경우처럼, “파라미터 중심”의 요청을 처리할 때 사용

> ⭐ 정리: @ModelAttribute는 요청 파라미터를 필드에 바인딩해서 객체 생성



| 항목           | @RequestBody             | @ModelAttribute          |
| ------------ | ------------------------ | ------------------------ |
| 데이터 읽는 곳 | HTTP Body                | Query/Form 파라미터          |
| 내부 동작        | JSON → 객체 (ObjectMapper) | 파라미터 → 객체(WebDataBinder) |
| 주 사용 사례      | REST API, JSON 기반 요청     | 검색 조건, HTML 폼 전송         |
